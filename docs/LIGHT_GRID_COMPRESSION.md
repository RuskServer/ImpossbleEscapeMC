# 光格子の区画圧縮試作

本番の送信・描画形式は変更していない。tools/light_grid_codec.pyは現在のiem:light payloadを読み、近距離の4bit格子だけを4×4×4区画へ可逆圧縮する。均一、2値、3〜4値、4bit直接格納を区画ごとに選び、短い方式を使う。境界の端数にも対応。復号時は寸法上限、モード、パレット、長さを検証する。

実際のSunShadowService.computeLightに既存テストの壁地形を与えた48×16×48の結果は、光格子21068bytesに対し、屋外3442bytes、空光5で2602bytes、空光0で2434bytes。実レイドの記録ではなく、単純な地形の試験値である。光種別と遠景、ヘッダーは圧縮対象外。現行データもDEFLATEで473/391/384bytesになるため、ネットワーク圧縮後の効果を未圧縮サイズだけから判断してはいけない。

80×16×80の合成データでは、均一3210bytes、各区画2値19210bytes、4値35210bytes、16値52810bytes。複雑な格子は密詰め51200bytesより増える。区画圧縮だけで常に旧容量へ収まる保証はない。

## Modの有無

初案の受信時CPU復号はMod限定。確認したIEM_CompatibilityのLightDataは512×33テクスチャで容量16384wordに切り詰めるため、展開後の格子を広げるにはこちらも拡張が必要。

Modなしでは、文字経由の圧縮データを既存light_gridパスでGPU復号する方式が候補。その場合は区画へのランダムアクセス索引を追加し、キャッシュ・格子のサイズとデータ検証を更新する必要がある。現在の試作形式は逐次復号専用で、シェーダーへ接続済みではない。16bitのbyte位置索引を仮定すると48×16×48で1152bytes、80×16×80で3200bytesを別途要する。14bit文字への再梱包、原点・世代の一括更新、途中受信の拒否も設計が必要。

## 次の判断材料

実レイドからiem:light payloadを取得して試作ツールへ渡す。実マップでの圧縮率、索引込み容量、CPU/GPUの復号時間、実際のネットワーク圧縮後の転送量を測る。その後に中距離廃止・遠景縮小と近距離の寸法を決める。本番取得機能、Mod/パックへの組込み、範囲変更は未実装。

検証: python tools/check_light_grid_codec.py。各方式・端数区画・48/80格子の完全復元、欠損・不正パレット・余剰データ拒否を確認。

## 索引付きGPU復号の単体計測

`tools/bench_light_grid_gpu.py`を追加。元のILG1本体からヘッダーを外し、各区画の先頭byte位置を16bitの索引として前置する。索引・本体を連続したbit列として14bit wordへ再梱包する。GLSL 330の通常のRGBA8 sampler2Dからwordを取得し、索引→モード→必要な値だけを読む。逐次走査はしない。寸法は4の倍数に限定した計測用形式で、本番のヘッダー・有効性管理は未実装。

比較側は現行の7セル/28bitの条件付き読み出し、出力は両方式とも明るさ変換と日向bitを含むRGBA8とした。出力範囲は近距離格子のみで、種類格子の行は含まない。復号した4bit値も出力alphaからCPUの元値と照合し、13ケースすべて完全一致した。48格子の壁地形3ケース、48/80格子の均一・2値・4値・16値・混在区画を使用。混在は区画ごとに方式を無作為に選び、全方式が同時に存在する。

2026-10-30、RTX 3060、EGL/OpenGLで計測。16回ウォームアップし、64drawをGPU timer queryで囲んだ平均を15組取り中央値を使用。両方式の順序を交互に入れ替え、読戻し・アップロード・Pythonの処理時間をGPU計測から外した。48/80の固定テクスチャを毎フレーム展開する想定であり、更新時だけ展開できるという仮定は置いていない。

| データ | 現行の復号 ms/draw | 索引付き復号 ms/draw | 索引込み14bit再梱包後 bytes |
| --- | ---: | ---: | ---: |
| 48×16×48 壁・空光15 | 0.001008 | 0.002240 | 5240 |
| 48×16×48 全方式混在 | 0.001024 | 0.003088 | 13074 |
| 80×16×80 区画ごと2値 | 0.002656 | 0.007712 | 25600 |
| 80×16×80 全方式混在 | 0.002656 | 0.008048 | 35414 |
| 80×16×80 全区画16値 | 0.002656 | 0.005504 | 64000 |

未圧縮の比較は23wordの旧ヘッダー込みで48格子21114bytes、80格子58562bytes。圧縮側の表は索引込みだが新プロトコルのヘッダー・種類・遠景を含まない。byte列を14bit wordに格納して2byte/wordで送るため、単なる圧縮byte数より転送表現が増える。現在の16384word（32768bytes）には80格子の混在ケースは近距離だけでも収まらない。計測時は容量超過ケースの入力テクスチャを拡張した。本番でこの容量が使えることを意味しない。

結論: このGPUの単体計測では復号の増分は約0.001〜0.006msで、索引付き可変長形式を避ける根拠になる負荷は見られなかった。一方、複雑なデータの容量保証は解決していない。実マップでの圧縮率と容量超過時の方式を次に検討する。

これは実Minecraftフレーム時間ではない。キャッシュが温まった連続drawのスループットであり、実ゲームでの初回アクセス、GPU競合、font→sun_cache経由、検証・ヘッダー処理、種類格子、低性能GPUの負荷は未計測。Pythonでのencode＋CPU照合時間もJSONへ記録するが、Java実装の速度として扱わない。元の試作の可逆テストも再実行して成功。計測結果JSONは`local/compression/gpu.json`に保存し公開対象外。

## 実環境検証モード（2026-10-30追加）

上記は単体試作の記録。今回、`LightGridCompression`とパックの`iem_sun.glsl`を接続し、現行48×16×48の範囲を維持した比較用モードを追加した。新しいプラグインとパックを両方入れる。Modの追加変更は不要（既存のiem:lightチャンネルとword 3の印を維持）。初期状態は従来形式。新モードは本人だけ、ログアウトで解除、再起動後もOFF。

1. レイド中、または`/shaderdebug sun`で光の送信を有効にする。
2. `/shaderdebug sun compression on`で本人の圧縮試験を有効にする。
3. 次の光データ更新を待ち、`/shaderdebug sun compression status`で近距離の従来/送信bytes、全体bytes、Java encode時間を確認する。移動・時刻変更・最大約10秒の定期更新で再計算する。
4. 屋外、屋内、壁際、窓、光源、遠景、夜、移動中で、影の位置・明るさ・色が変わらないか、更新時のちらつき・保持の長さ・GPU時間を比較する。Modあり/なしは別々に確認する。
5. `/shaderdebug sun compression off`で従来形式へ戻す。これも次の更新で切り替わる。

圧縮計算は既存の光計算と同じ非同期タスクで行う。圧縮しても小さくならない場合、または全体が容量上限を超える場合、現行48格子では従来の送信へ戻す。範囲拡大・中距離削除・遠距離変更は今回含まない。

送信形式: word 0=0x14C1（圧縮時のみ）、1=圧縮近距離のword数、2=予約の0、3以降は従来ヘッダー。word 23から、区画先頭byte位置のlittle-endian uint16配列と区画本体を連結し、下位bitから14bitずつ詰める。区画位置はy,z,x順、内部もy,z,x順。区画本体はPython試作と同じmode 0/1/2/3。本体先頭からのbyte位置を索引に入れる。種類・遠景はword 1で指定する近距離の直後へ置く。従来形式はword 0/1を0に戻す。新パックは両形式を読む。

文字経由では`sun_ready`（1×1）の段で到着を確認し、新形式とその解除時は全wordがそのフレームに到着してから`sun_cache`を更新する。欠けた・ずれたフレームでは索引・本体・原点をまとめて前の値に保つ。Mod経由は既存の一括テクスチャ更新を使う。従来形式だけの時は以前のセル単位更新を維持する。到着確認は新形式のフレームごとに走るので、文字が画面上に揃わない状態では古い光が保持される可能性があり、実機で確認する。

検証: Javaの12格子round-trip、Java/Python送信表現の一致、Java出力→実際のパックのGLSLで全セル一致、全方式混在、長さ上限拒否。到着確認は正常・欠損・位置ずれ・過大長・クリア・従来形式への切替・Mod優先をGPUで確認した（画面配置だけ線形の試験配置へ置換）。到着確認の単体GPU中央値はRTX 3060で約0.0844ms。これは上記の復号時間とは別で、実MinecraftのGPU時間は未測定。
