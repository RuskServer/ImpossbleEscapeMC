# 自然な光と色に近づける描画改良

目標はSTALKER 2、Cyberpunk 2077のパストレーシング、Cyclesで見られる、光源・反射・遮蔽がつながった空間の見え方。今回は既存のサーバー光とリソースパックのポスト処理を拡張する。

## 既存の構成と今回の変更

`SunShadowService` は近傍の48×16×48ブロックについて太陽の可視性、ブロック光、12方向の1回反射を計算し、圧縮した格子をクライアントへ送っている。格子の1マスは面の向きやRGB反射率を持たず、シェーダーが倍率と光の種類を補間して適用する。

旧反射処理はヒットした面の前の空気にある日光の量をそのまま使い、面に背を向ける日光まで跳ね返していた。レイが最後に通過した軸からヒット面の外向き法線を取り、日光の入射を `max(dot(normal, sun), 0)` で重み付けする。途中の部分透過ブロックも透過率を掛け、低透過率の経路を打ち切る。既存のスナップショット・非同期計算・更新間隔・データ容量・パケット形式は維持する。ブロック光は方向を持たないスカラーのままなので、今回の面の入射補正は日光に対するもの。

リソースパックには `iem:post/indirect` を追加する。深度から復元した近くの面の位置・法線と、その面の画面上の色を使い、面どうしが向き合う場合の色の回り込みと接地の遮蔽を求める。固定6標本、最大半径1.25ブロック。候補との間の2点も確認し、途中に手前の遮蔽物があれば色を集めない。12〜24ブロックで効果を減らす。

画素ごとのRGB反射光は各成分0.08以下、接地の暗さは15%以下。ガンマ2.2による光量の近似空間で合成し、暗い面を一定の白い光で持ち上げない。空・一人称の手・有効な深度や法線がない場所には追加効果をかけない。履歴を使わず、固定標本なので時間ノイズと残像を追加しない。

既存 `light.fsh` の深度・法線復元を `iem_surface.glsl` にまとめ、同じ規則で細い輪郭や深度の飛びを除外する。960×540の処理結果は画面側で深度を比較しながら拡大する。通常・暗視・バイザー・雨の全12種のgradeに同じ段を入れる。反射光の元はバイザーの汚れが入る前のワールド画像を使う。

## 調整と比較

パックの `tools/post_effects.py` が設定と段の並びの正本。`python tools/post_effects.py contents` で再生成する。`IndirectConfig` は次の値。

| 設定 | 初期値 | 用途 |
| --- | ---: | --- |
| Radius | 1.25 | 近傍の探索半径（ブロック） |
| BounceStrength | 1.1 | 画面から集める反射光の強さ |
| ContactStrength | 0.6 | 接地の遮蔽の強さ |
| MaxBounce | 0.08 | RGBごとの反射光の上限 |

BounceStrengthとContactStrengthを両方0にすると、この段の見た目を無効にして比較できる。処理コスト自体は残る。半径を0にすると早期終了する。反射光の設定と、以下のグレーディング設定は個別に調整する。光の表の一律補正は維持する。

## 検証

- `SunBounceTest`: 実際のレイと壁で、正面・背面・平行・斜めの日光、夜のブロック光、部分透過、吸収する面を確認。
- `SunShadowServiceTest`: 日なた・日陰・室内・夜の光源・遠景・圧縮データの互換性を確認。
- `tools/check_shaders.py`: 対象クライアントのincludeを使い、IEM_MOD有無を含む164組をVulkan向けにコンパイル。今回変更しないSodium固有の地形2段は、この実行では対象外。
- frameとlight/indirect/gradeの組をVulkan向けにリンクし、SPIR-Vを検証。
- 実際のindirectフラグメントをGPUで実行し、出力の有限性・上限、空と一人称の手の除外、mod有無を確認。部屋の角を生成した比較画像で接地と面間の寄与も確認。
- 同じ検証場面で、入力1920×1080、追加段960×540、RTX 3060の測定は約0.2〜0.3ms。フラグメントの試験はOpenGLドライバ上で行った値で、MinecraftのVulkan実行時の全体性能や実マップの最悪負荷を保証しない。既存gradeへの合成を含む同場面の増分は約0.3〜0.4ms。実際の旧・新gradeフラグメントでも、追加段が中立値なら従来出力を維持すること、空・手の深度で出力差が出ないことを確認した。

## 残る範囲と実機確認

これはLDR画面を用いた小さな拡散反射の補助。正確なアルベド・材質・粗さ・HDR放射輝度を受け取るG-bufferや、ワールド全体の加速構造を持つパストレーサーではない。画面外・裏側・透明面を正確に追えず、カメラの向きで反射の寄与が変わる可能性がある。遮蔽の2点確認も厳密な可視性証明ではない。サーバー格子の光を基本とし、画面からの寄与は近距離に限定する。

金属の鏡面反射、ガラスの屈折、画面外の色反射、多段反射、正確なHDR・露出・トーンマッピングは次段階。これらには材質の入力と描画経路の拡張を検討する。大きな実装へ進む前に、実マップで窓際の室内、壁と床、暗室、夜、細いフェンス、銃とADS、暗視、バイザー、画面端とカメラ移動を比較する。現在の比較画像は生成した検証用の場面で、Minecraftの実機キャプチャではない。

参考: [PBRTの拡散反射モデル](https://www.pbr-book.org/3ed-2018/Reflection_Models/Lambertian_Reflection)、[Epicのスクリーントレースの制約](https://dev.epicgames.com/documentation/unreal-engine/lumen-technical-details-in-unreal-engine)。コードは本プロジェクトの既存処理と独自の限定的な近傍サンプリングによる。

## グレーディングとハイライト圧縮

従来の低彩度・青い影と暖色の明部・周辺減光・グレインを弱め、光源や素材の色が見える方向へ調整する。通常のgradeと暗視・バイザーを含む12種を同じ正本から生成する。

| 設定 | 従来 | 新しい値 |
| --- | --- | --- |
| Saturation | 0.85 | 0.98 |
| Contrast | 1.08・直線 | 1.02・黒白を保持するS字 |
| ShadowTint | 0.95 / 0.99 / 1.06 | 0.99 / 1.00 / 1.015 |
| HighlightTint | 1.03 / 1.00 / 0.95 | 1.01 / 1.00 / 0.99 |
| Vignette | 0.22 | 0.08 |
| Grain | 0.025 | 0.003 |
| 周辺の色収差 | 0.45画素係数 | 0・無効 |

フレアの近い光芒、横線、ゴースト、レンズ汚れも抑える。暗視装置のセンサーを表す専用グレインと、被弾・出血等の演出設定は維持する。

`iem_tonemap.glsl` は本プロジェクト独自のソフトショルダーとsRGB変換を持つ。IEMが加える光とフレアを最終段で近似線形光量へまとめ、手動Exposure=1.0を掛ける。RGBの最大成分が0.7以下ならトーンカーブは恒等。超えると指数型の肩で1へ漸近させ、RGBを同率で縮小する。入力のピークが1を超える強い色光は徐々に白へ寄せる。暗部と中間調へトーンカーブの減光をかけず、成分別クリップによる強い色光の黄・シアン等への変色を抑える。直線コントラストも廃止し、出力0と1を保つS字にする。

`ToneMapConfig` の Exposure=1.0、ShoulderStart=0.7、HighlightDesaturation=0.12、ToneMapStrength=1.0が初期値。ToneMapStrength=0でハイライト圧縮を無効化できる。自動露出による室内外の明るさの追従は加えない。

対象クライアントのメイン描画先はRGBA8_UNORMで、入力はすでに描画されたSDR画像。元の画面でクリップ済みの情報は復元できない。圧縮できるのは、この段で加算・増幅するIEMの光やフレアの浮動小数点値を含む範囲。シーン全体をHDR描画するAgX/ACESやCyclesのカラーマネジメントと同じ実装ではない。暗視やEMPを含む実機で最終的な強さを比較する。

`tools/check_tonemap.py` は実際のGLSLをGPUへ渡し、8192点の高輝度ランプ、暗部・中間調の恒等性、出力の単調性と範囲、sRGB往復、色の順序、黒潰れを増やさないコントラスト、圧縮の無効化を検証する。実行例: `uv run --with moderngl --with numpy python tools/check_tonemap.py`（ヘッドレスGL/EGLが必要）。通常のVulkan向け164組コンパイルとframe/gradeのリンクも確認する。

生成した部屋を実際の旧・新gradeフラグメントで描き、有限な出力と空・手の間接光除外を確認した。比較画像は検証用の生成シーン。既存のゲームキャプチャへ二重にグレーディングして比較した画像ではない。RTX 3060の同場面では、この色調改良によるgrade段の増分は約0.04msだった。ゲーム全体の実測値ではない。

守色とハイライトの扱いの参考: [Khronos PBR Neutralの説明](https://github.com/KhronosGroup/ToneMapping/blob/main/PBR_Neutral/README.md)。ここでは同実装の黒レベル補正やコードをコピーせず、SDR入力に合わせた独自の曲線を使う。
